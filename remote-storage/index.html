    Remote storage¶

    ← docs index

    .quarantine/ on a local disk is exactly right for a script on your laptop — and exactly wrong for Kubernetes, AWS Lambda, Docker, or any fleet of workers whose disks evaporate with the container. Remote backends give all of them one shared quarantine: workers set failures aside in a bucket or container, and you inspect and replay them from your own machine.

    Dedicated Cloud Storage Guides¶

    Detailed setup, credentials, least-privilege IAM policies, FAQs, and consistency guarantees are documented for each provider:

    • AWS S3 Guide (s3://bucket/prefix) — IAM roles, IRSA, ECS tasks, KMS, and LocalStack.
    • Google Cloud Storage (GCS) Guide (gs://bucket/prefix) — ADC, GKE Workload Identity, CMEK, and fake-gcs-server.
    • Azure Blob Storage Guide (azure://container/prefix or az://) — Entra ID Managed Identity, connection strings, AKS Workload Identity, RBAC, and Azurite.

    Using the S3 backend¶

    Install the extra (the core package stays zero-dependency):

    pip install "quarantine-py[s3]"

    Then a URL goes anywhere a folder went — the same dir=, the same --dir, the same $QUARANTINE_DIR:

    @quarantine(dir="s3://my-bucket/etl/quarantine")
def process(item): ...

    quarantine list  --dir s3://my-bucket/etl/quarantine
quarantine show 2 --dir s3://my-bucket/etl/quarantine
quarantine retry --dir s3://my-bucket/etl/quarantine --import job.py
quarantine ui    --dir s3://my-bucket/etl/quarantine
export QUARANTINE_DIR=s3://my-bucket/etl/quarantine   # or set it once

    Every command behaves as it does locally, because records are what they are locally: per-record objects (0001/meta.json, input.pkl, traceback.txt, …) under the prefix, byte-for-byte the same files. Reads are cached in a per-URL directory under the system temp folder so show, debug, retry and the dashboard work unchanged.

    Credentials¶

    The backend uses boto3's standard credential chain — nothing quarantine-specific to configure. In order, boto3 looks at:

    1. AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY (and AWS_SESSION_TOKEN) environment variables,
    2. the shared config/credentials files (~/.aws/credentials, with AWS_PROFILE selecting a profile), including SSO sessions,
    3. the compute role: ECS task role, EKS IRSA / Pod Identity, Lambda execution role, or the EC2 instance profile.

    In a fleet, that usually means: workers use their task/pod role, your laptop uses your SSO profile — same URL, different credentials, no keys in code. AWS_ENDPOINT_URL is honoured too, so S3-compatible stores (MinIO, LocalStack) work.

    IAM permissions¶

    The backend needs four S3 actions, and they can be scoped to the exact bucket and prefix. A minimal policy for a worker or operator (writes records, retries, clears):

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "QuarantineList",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::my-bucket",
      "Condition": {
        "StringLike": { "s3:prefix": "etl/quarantine/*" }
      }
    },
    {
      "Sid": "QuarantineReadWrite",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::my-bucket/etl/quarantine/*"
    }
  ]
}

    What each action is for:

    Action Used by
    s3:ListBucket (on the bucket, prefix-scoped) every read: list, stats, deduplication, finding the next free id
    s3:GetObject show, retry, debug, the dashboard — downloading records
    s3:PutObject quarantining (including the conditional id claim), retry bookkeeping
    s3:DeleteObject retry (recovered records are deleted), clear, reindex sweeps

    Two useful reductions:

    • Read-only inspection (a dashboard host, an on-call engineer who may look but not touch): drop s3:PutObject and s3:DeleteObject. list, show, stats and the dashboard's viewing work; quarantining, retry and clear will fail with an access error, as intended.
    • Write-only workers are not possible: writers also need ListBucket and GetObject, because allocating an id requires seeing which ids exist and deduplication reads existing records.

    No bucket-management permissions are needed — the backend never creates buckets, never touches bucket policy, and works fine on a prefix of a shared bucket. If the bucket uses SSE-KMS encryption, add kms:Decrypt and kms:GenerateDataKey on the bucket's key. And since records contain your real inputs, treat the prefix like the data it holds: block public access, encrypt at rest, and remember redact= runs before upload, so secrets you name never reach the bucket at all.

    The guarantees, translated to S3¶

    The local folder's promises rest on atomic renames and atomic directory creation — neither exists on S3, so they are replaced (the reasoning lives in ADR 0007):

    • A reader never sees a partial record. meta.json is uploaded last and is the commit point: a record without it does not exist, whatever else has been uploaded. A crash mid-write leaves invisible debris, and quarantine reindex --dir s3://… sweeps it.
    • Two workers can never claim the same id. An id is claimed by writing a zero-byte .claim object with If-None-Match: * — S3's conditional write, which the loser sees as PreconditionFailed and simply takes the next number.
    • Deduplication is advisory under concurrency. Two workers quarantining the same input in the same instant may both store it — a duplicate record, never a lost one. Never lose a failure outranks never store twice.
    • There is no index.json object. S3 listings are strongly consistent, so the listing is the index; nothing can go stale.

    GCS credentials¶

    The backend uses google-cloud-storage's standard Application Default Credentials (ADC) chain — nothing quarantine-specific to configure. In order, the client looks at:

    1. the GOOGLE_APPLICATION_CREDENTIALS environment variable, pointing at a service-account key file,
    2. user credentials from gcloud auth application-default login,
    3. the attached runtime identity: a GKE Workload Identity binding, a Cloud Run/Cloud Functions service account, or a Compute Engine instance's attached service account.

    In a fleet, that usually means: workers use their attached service account, your laptop uses gcloud auth application-default login — same URL, different credentials, no keys in code. STORAGE_EMULATOR_HOST is honoured too, so a local fake-gcs-server works for development and testing without touching a real bucket.

    GCS IAM permissions¶

    The backend needs the storage object actions, scoped to the bucket. The roles/storage.objectUser predefined role covers exactly this — list, read, create and delete objects, with no bucket-management permissions — for a worker or operator (writes records, retries, clears):

    gcloud storage buckets add-iam-policy-binding gs://my-bucket \
  --member="serviceAccount:worker@my-project.iam.gserviceaccount.com" \
  --role="roles/storage.objectUser"

    If you'd rather write a custom role, the underlying permissions are storage.objects.list, storage.objects.get, storage.objects.create and storage.objects.delete.

    What each permission is for:

    Permission Used by
    storage.objects.list every read: list, stats, deduplication, finding the next free id
    storage.objects.get show, retry, debug, the dashboard — downloading records
    storage.objects.create quarantining (including the conditional id claim), retry bookkeeping
    storage.objects.delete retry (recovered records are deleted), clear, reindex sweeps

    Two useful reductions:

    • Read-only inspection (a dashboard host, an on-call engineer who may look but not touch): use roles/storage.objectViewer instead. list, show, stats and the dashboard's viewing work; quarantining, retry and clear will fail with an access error, as intended.
    • Write-only workers are not possible: writers also need list and get, because allocating an id requires seeing which ids exist and deduplication reads existing records.

    No bucket-management permissions are needed — the backend never creates buckets and works fine on a prefix of a shared bucket. If the bucket uses a customer-managed encryption key (CMEK), add cloudkms.cryptoKeyEncrypterDecrypter on that key. And since records contain your real inputs, treat the prefix like the data it holds: keep the bucket private, encrypt at rest, and remember redact= runs before upload, so secrets you name never reach the bucket at all.

    The guarantees, translated to GCS¶

    The local folder's promises rest on atomic renames and atomic directory creation — neither exists on GCS, so they are replaced with GCS's own primitives (the reasoning lives in ADR 0007):

    • A reader never sees a partial record. meta.json is uploaded last and is the commit point: a record without it does not exist, whatever else has been uploaded. A crash mid-write leaves invisible debris, and quarantine reindex --dir gs://… sweeps it.

    Azure credentials¶

    The backend supports standard Azure authentication mechanisms:

    1. AZURE_STORAGE_CONNECTION_STRING environment variable (ideal for connection strings and local development with Azurite),
    2. AZURE_STORAGE_ACCOUNT_NAME (or azure://account@container/prefix) along with an account key (AZURE_STORAGE_KEY or AZURE_STORAGE_ACCOUNT_KEY) or SAS token (AZURE_STORAGE_SAS_TOKEN),
    3. Azure Active Directory / Entra ID via DefaultAzureCredential (when azure-identity is installed): AKS Workload Identity, Azure Managed Identity (VM, Container Apps, App Service), or Azure CLI credentials (az login).

    In a fleet, that usually means: workers use their Managed Identity or connection string, your laptop uses Azure CLI credentials or a dev connection string — same URL, different credentials, no keys in code. AZURE_STORAGE_EMULATOR_HOST (or AZURE_BLOB_ENDPOINT_URL) is honoured too, so a local Azurite instance works for development and testing without touching a real storage account:

    docker run -d -p 10000:10000 mcr.microsoft.com/azure-storage/azurite

    Azure RBAC permissions¶

    The backend needs blob data actions scoped to the container. The built-in Storage Blob Data Contributor role covers exactly this — list, read, write and delete blobs, with no storage-account management permissions — for a worker or operator (writes records, retries, clears):

    az role assignment create \
  --assignee "<managed-identity-principal-id>" \
  --role "Storage Blob Data Contributor" \
  --scope "/subscriptions/<sub-id>/resourceGroups/<rg>/providers/Microsoft.Storage/storageAccounts/<account>/blobServices/default/containers/my-container"

    What each permission is for:

    Permission Used by
    Microsoft.Storage/storageAccounts/blobServices/containers/blobs/read every read: list, stats, deduplication, downloading records (show, retry, debug, dashboard)
    Microsoft.Storage/storageAccounts/blobServices/containers/blobs/write quarantining (including the conditional id claim), retry bookkeeping
    Microsoft.Storage/storageAccounts/blobServices/containers/blobs/delete retry (recovered records are deleted), clear, reindex sweeps

    Two useful reductions:

    • Read-only inspection (a dashboard host, an on-call engineer who may look but not touch): use Storage Blob Data Reader instead. list, show, stats and the dashboard's viewing work; quarantining, retry and clear will fail with an access error, as intended.
    • Write-only workers are not possible: writers also need list and read permissions, because allocating an id requires seeing which ids exist and deduplication reads existing records.

    No container-management permissions are needed — the backend never creates containers and works fine on a prefix of a shared container. And since records contain your real inputs, treat the container like the data it holds: keep it private, encrypt at rest, and remember redact= runs before upload, so secrets you name never reach Azure at all.

    The guarantees, translated to Azure Blob Storage¶

    The local folder's promises rest on atomic renames and atomic directory creation — neither exists on Azure Blob Storage, so they are replaced with Azure's own primitives (the reasoning lives in ADR 0007):

    • A reader never sees a partial record. meta.json is uploaded last and is the commit point: a record without it does not exist, whatever else has been uploaded. A crash mid-write leaves invisible debris, and quarantine reindex --dir azure://… sweeps it.

    Using the Redis backend¶

    See the dedicated Redis Remote Storage Guide for full URL options, TLS, Cluster hash tags, TTL memory management, and Docker setup.

    For short-lived, high-churn quarantines where an object store is overkill, install the redis extra:

    pip install "quarantine-py[redis]"

    Use a redis:// (or rediss:// for TLS) URL anywhere a folder went:

    @quarantine(dir="redis://localhost:6379/0?prefix=etl:quarantine&ttl=3600")
def process(item): ...

    quarantine list  --dir "redis://localhost:6379/0?prefix=etl:quarantine"
quarantine retry --dir "redis://localhost:6379/0?prefix=etl:quarantine" --import job.py

    Records are stored atomically as Redis hashes under {<prefix>}:record:<id> (default prefix quarantine), with ids allocated via INCR on {<prefix>}:next_id. Optional ttl (in seconds) expires each record hash automatically.

    Using the Databricks Unity Catalog Volumes backend¶

    See the dedicated Databricks Unity Catalog Volumes Guide for full authentication chains, Unity Catalog GRANT statements, and commit-point details.

    To store quarantined records inside a governed Databricks Unity Catalog Volume, install the databricks extra:

    pip install "quarantine-py[databricks]"

    Pass a /Volumes/<catalog>/<schema>/<volume>[/<prefix>] path anywhere a folder went:

    @quarantine(dir="/Volumes/main/analytics/quarantine/etl")
def process(item): ...

    quarantine list  --dir /Volumes/main/analytics/quarantine/etl
quarantine retry --dir /Volumes/main/analytics/quarantine/etl --import job.py

    Authentication uses databricks-sdk's standard WorkspaceClient() chain (DATABRICKS_HOST + DATABRICKS_TOKEN, ~/.databrickscfg, OAuth/instance identity, or Databricks runtime credentials). Required Unity Catalog privileges are USE CATALOG, USE SCHEMA, READ VOLUME, and WRITE VOLUME (drop WRITE VOLUME for read-only inspection). Records follow the same layout and commit-point guarantees as S3/GCS/Azure (ADR 0007), claiming ids with .claim (overwrite=False) and committing with meta.json last.

    macOS note: Any /Volumes/... path is routed to DatabricksVolumeStore. To store a local quarantine on a macOS external drive mounted under /Volumes/<DriveName>, instantiate quarantine.Store("/Volumes/...") directly.

    Writing your own backend¶

    The interface is public and small. Subclass quarantine.StorageBackend, implement its methods (the docstrings state the contract, and Store — the local folder — is the reference implementation), and claim a URL scheme:

    from quarantine import StorageBackend, register_backend


class MyStore(StorageBackend):
    def __init__(self, url: str) -> None: ...

    # exists, ensure, records, get, count, add, update, write_traceback,
    # delete, clear, purge_temp, rebuild_index, fingerprints, disk_bytes


register_backend("mystore", MyStore)

    From then on dir="mystore://…" works everywhere a path does. Whatever the transport, keep the two promises: a reader never sees a partial record, and a failed write never silently loses one.

    The interface above is how built-in backends are implemented, and how you can build and register your own custom backend.
